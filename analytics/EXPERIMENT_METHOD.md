# Reproducible demand forecasting experiment

Run `python analytics/compare_product_demand.py --data database/packaged-data-next --output analytics/experiments/<new-run-id>` with the dependencies in `analytics/requirements.txt` plus `joblib`. The updated `train_product_demand_colab.ipynb` follows the lecturer's local code → GitHub commit → Google Colab → Google Drive → local review workflow. Push the new code/data first, paste the exact commit hash into the notebook, and keep the full output folder. Every run requires a new output path and never overwrites previous evidence.

The target is cases in accepted customer orders, including the one still-dispatched order after a failed delivery attempt, summed per product over the next 7 or 30 **calendar** days. It excludes cancelled and draft requests. Each 7-day origin is Sunday, so the target is Monday through Sunday. The 30-day experiment also uses Sunday origins for comparable weekly sampling. Sundays are known closed days with zero demand. Features are the historical lags, rolling summaries, recent weekly change, and seasonal terms already present in `product_forecast.py`. They use information dated at or before each origin; no future production, inventory, orders or labels enter an input. The historical benchmark repeats the previous period's demand. Random Forest and Gradient Boosting use the same feature vector and training dates. No random train/test shuffle is used.

Training labels finish by 31 December 2025. Validation origins fall after that date and their labels finish by 30 June 2026. Test origins follow validation and their labels finish by 5 November 2026. For test evaluation, models are refitted on labels fully known by 30 June, never on a later label. Fixed model parameters and seed are saved in each `config.json`; this experiment does not tune parameters on the test. Validation MAE chooses a method for each product/horizon. The test reports later performance and is **not** used to change that choice. Because earlier project work examined some late-2026 dates, these test dates are chronologically held out in this run but cannot honestly be called a never-seen external final test.

The evidence folder contains dataset metadata/hash, validation report, feature names and parameters, dependency versions, Git commit when available, actual-vs-predicted rows, per-product and overall MAE/RMSE/bias, SVG charts, fitted model files and execution log. Negative bias means predicted cases are below actual cases on average. The notebook also displays these results in Colab. A real company must supply genuine later orders before claiming practical accuracy.

The comparison evaluates **raw** Random Forest and Gradient Boosting with a fixed training cutoff in each split. AquaTrack's deployed 7-day routine retrains on each completed week and applies a correction from prior residuals; its 30-day routine uses its own rolling backtest. The notebook comparison therefore supports model comparison but is **not an exact evaluation of the deployed prediction procedure**. Do not present its scores as deployed-model scores or copy its saved model files into production.

The separate `evaluate_deployed_weekly.py` script replays `product_forecast.py::forecast_weekly` exactly at each selected Sunday origin, using only data known at that origin. It saves the CSV dataset SHA-256, model parameters, Python/NumPy/scikit-learn versions, origin dates, actual cases, predictions, corrections, and a previous-week benchmark. Run it with a fresh output directory: `python analytics/evaluate_deployed_weekly.py --data database/packaged-data-next --output analytics/experiments/<new-run-id>`. By default it evaluates every eligible Sunday in the validation and test periods. `--max-origins-per-split N` is a faster, explicitly sampled check and must not be reported as a full-period evaluation. This replay validates the **deployed weekly procedure** on synthetic history; it does not turn the notebook's fixed-cutoff comparison into a deployed Gradient Boosting comparison. Repeat both experiments after any future dataset replacement, and seek genuine later orders for an external check.
