# Dataset replacement and forecasting integration assessment

**Status: imported into an isolated MySQL clone and activated in the local XAMPP application on 5 November 2026 after the user's approval.** The original `water_management` database was left intact. A full SQL backup is stored in the workspace at `output/database-backups/water_management_before_20261105_import.sql` (SHA-256 `DFF1E64BC00FEB77ED0FEDB37234E7B670B2423D31EA785BDA9F203ABD1A0722`). The app's previous `.env` is saved as `.env.backup` in the XAMPP project; restoring it switches the app back to the original database. The active database is `water_management_demo_20261105`. Active user accounts and credentials were preserved; one inactive fictional manager was added as the historical policy-approval actor. The deployed Python model was not changed.

The versioned CSV schema is an exchange format. `dataset:import-next` maps it into Laravel's existing schema and only writes to the named demo database. The old `dataset:replace-packaged` command is tied to the 26 October files and must not be run against this folder. The application has no dedicated delivery-attempt table; the 34 failed attempts and 33 successful retries were imported as dated `audit_logs` events attached to dispatches. Quality transitions were imported as batch audit events. The unresolved delivery remains an active dispatched order/trip without an invoice. A future dedicated delivery-attempt UI would make those histories easier to inspect.

Before any replacement, take a verified full MySQL backup, record table counts and hashes, distinguish real entries from synthetic records, and use a cloned database with the same migrations and application configuration. Preserve users and credentials. Inventory, batch, order, invoice, payment, returns/credits, delivery-trip, forecast, production-plan, notification, audit, technical-event, and reporting tables have dependencies. The current importer deletes many of these, and its mapping does not cover the new trip and policy CSVs. Replacing old operations while retaining derived forecasts, profit records or audit references would create mixed history. Migration must map product IDs and zone codes to existing master rows and transform the new CSV columns into the exact Laravel schema, including actors, timestamps, policy approval records, quality evidence and trip lifecycle fields. Existing real events and audit entries must remain immutable; if a clean separation is impossible, use a dedicated demo database instead.

The new importer was run against the cloned Laravel/MySQL database. Counts matched the CSVs: 8,698 orders, 1,173 batches, 887 trips, 8,656 dispatches and 8,655 invoices. Read-only SQL checks found zero stock, order-total, invoice, payment, quality, Sunday or zone mismatches. AquaTrack's financial summary service ran on the clone, all four products produced 7- and 30-day forecasts, and 19 existing workflow tests passed with 282 assertions. The original database was not replaced. Future imports should still repeat these checks and preserve the verified backup.

The forecasting service fills missing calendar dates with zero, which is compatible with the new daily demand table. A narrow Laravel change now treats Sundays as closed when checking recent order-record completeness; the Python model, features and calculations were not changed. The deployed Python weekly method still uses residual bias correction and rolling retraining, whereas the comparison experiment evaluates fixed-cutoff raw models. This difference remains a limitation when interpreting the experiment scores. The 30-day view is exploratory. Recommendations require current 7-day forecasts, eligible stock, confirmed relevant commitments and approved unfinished production; historical forecasts must never create current production decisions.

An isolated smoke test in `analytics/check_forecast_compatibility.py` runs the unchanged Python 7-day and 30-day forecast for all four products using daily history through Sunday 1 November 2026; its results are saved as `analytics/experiments/synthetic_20261105_05/python_compatibility.json`. This proves the Python input shape and calendar work. It does **not** prove Laravel's live-date, closure, stock or planning integration.

The staged workspace and XAMPP application folder remain separate. The new source dataset, importer, notebook, and final experiment files were copied into the XAMPP project, and their dataset file hashes matched the staged source. The old database and full SQL backup are retained for rollback. Do not switch the Python model solely because it won on synthetic validation data.
